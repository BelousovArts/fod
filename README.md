# Препятствия на пути метро по лидару

Решение находит посторонние объекты в габарите пути по облаку лидара (ROS 2,
`sensor_msgs/PointCloud2`) и выдаёт по каждому кадру статус пути: **СВОБОДНО**,
**ПРЕПЯТСТВИЕ** (с расстоянием и списком объектов) или **НЕ ГОТОВ** (путь ещё не найден).

## Запуск в 3 команды

Нужны Docker, видеокарта NVIDIA с драйвером ≥ 570 и
[nvidia-container-toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html).

```bash
# 1. Собрать образы (один раз, ~10 мин; нужно ~20 ГБ свободного места, образ — 13 ГБ)
docker build -t fod -f docker/Dockerfile .                      # узел и инструменты
docker build -t fod-viz --target viz -f docker/Dockerfile .     # то же плюс RViz2

# 2. Прогнать запись: результат в results/<имя записи>/
./run_bag.sh /путь/к/записи            # detections.csv, obstacles.csv, summary.json
./run_bag.sh /путь/к/записи --video    # плюс video.mp4

# 3. Живой режим с RViz: запись по кругу или настоящий лидар
./run_live.sh /путь/к/записи            # узел + RViz + ros2 bag play --loop
./run_live.sh /путь/к/записи --rate 0.5
./run_live.sh --topic /lidar_points     # живой лидар в сети (нужен DISPLAY / WSLg)
```

`-u` обязателен, если узел и источник облака — разные процессы: они должны работать
от одного пользователя, иначе общая память DDS недоступна и облака (десятки МБ)
не доходят. `run_live.sh` и `docker compose` это учитывают.

Запись — папка с `metadata.yaml` (sqlite3 или mcap) или файл `.db3` / `.mcap` в ней.
Топик облака находится сам (первый `PointCloud2`), задать явно: `--topic`,
или `topic` в `config/train.yaml`.

## На поезде

Служба с автозапуском и перезапуском при сбое. Параметры — `config/train.yaml`
(топик, установка лидара, GPU). После правки YAML: `docker compose restart fod`.

```bash
docker compose up -d --build
docker compose logs -f fod
# ROS_DOMAIN_ID — как у драйвера лидара:
ROS_DOMAIN_ID=5 FOD_UID=$(id -u) FOD_GID=$(id -g) docker compose up -d
```

`FOD_UID` / `FOD_GID` — тот же пользователь, что и драйвер лидара (по умолчанию root,
как у драйвера в своём контейнере).

**Установка лидара.** Тракт считает, что вперёд по ходу — ось −y, вверх — +z
(так стоят лидары в записях хакатона). Если у вас иначе — в `config/train.yaml`
или ключами `--forward` / `--up` / `--rpy`:

| Параметр | Смысл | Пример |
|---|---|---|
| `forward` | какая ось лидара смотрит вперёд по ходу | `-y` (по умолчанию), `+x`, `-x`, `+y` |
| `up` | какая ось смотрит вверх | `+z` или `-z` (лидар вверх ногами) |
| `rpy` | поправки, градусы: крен, тангаж, рыскание | `[0, 0, 0]`; крен + — верх наклонён вправо, тангаж + — смотрит вниз, рыскание + — повёрнут влево |

Облако сразу переводится в систему тракта; `/fod/status`, `/fod/obstacles` и маркеры
снова в системе лидара.

**Если узел отстаёт.** Он всегда берёт самый свежий кадр и пропускает старые:
отставание не копится. В `/fod/status` — `dropped` и `latency_ms`. Подписка по
умолчанию RELIABLE (облако — десятки МБ; при BEST_EFFORT потеря фрагмента теряет
весь кадр). Если драйвер отдаёт только BEST_EFFORT — `best_effort: true`.

## Инструменты по записи

Один и тот же детектор, что на поезде. Без Docker: `FOD_NO_DOCKER=1`.

```bash
./run_tool.sh video /путь/к/записи [--start 20 --until 80]   # video.mp4 + CSV
./run_tool.sh rerun /путь/к/записи [--until 60]              # rerun.rrd
./run_tool.sh map   /путь/к/записи                           # map.ply / map.pcd, вид сверху
./run_tool.sh stand /путь/к/записи --object person@80 --video
./run_tool.sh stand /путь/к/записи --scenario config/stand_example.yaml
./run_tool.sh stand --list                                   # типы объектов
```

У всех есть `--forward` / `--up` / `--rpy`. Результат — в `results/<запись>/`
(или `FOD_RESULTS`).

- **Видео** — range image спереди, вид сверху, панель: скорость, рекомендуемая
  скорость, дальность габарита, препятствия и графики за 60 с.
- **rerun** — 3D в системе поезда (облако в нескольких раскрасках: интенсивность,
  высота, дальность, габарит — переключаются в левой панели), карта мира, виды
  спереди и сверху, графики. Открыть: `rerun results/<запись>/rerun.rrd`.
- **Карта** — облако всей записи в мире, вид сверху и плитки по 100 м,
  траектория, места препятствий.
- **Стенд** — вставить объекты в запись и посмотреть, с какого расстояния
  детектор их заметил и подтвердил (`report.json`, `episodes.csv`).

## Что выдаёт

**Офлайн** (`results/<запись>/`):

| Файл | Содержимое |
|---|---|
| `detections.csv` | по кадру: `status` (UNKNOWN / CLEAR / OBSTACLE), `distance_m` до ближайшего препятствия, число препятствий, `reach_m` — до куда виден путь, скорость, время обработки |
| `obstacles.csv` | подтверждённые препятствия по кадрам: номер трека, расстояние вдоль пути, смещение от оси, высота над полотном, число точек, координаты в системе лидара, на каком расстоянии трек впервые замечен и впервые подтверждён |
| `summary.json` | итог: сколько кадров в каждом статусе, каждое препятствие — на каком расстоянии впервые подтверждено и сколько кадров держалось, время на кадр |
| `video.mp4` | с `--video` |

**Живой узел** (`python3 -m fod_ros.node`, `docker compose`, `./run_live.sh`):

- `/fod/status` — `std_msgs/String` с JSON: статус, расстояние, список препятствий
  и подозрений (`distance`, `offset`, `height`, `x`, `y`, `z`, `first_seen`),
  до куда известен путь, время обработки, задержка, сколько кадров принято и
  пропущено; `telemetry` — уровень (CLEAR / ATTENTION / OBSTACLE), скорость,
  рекомендуемая скорость, тормозной путь;
- `/fod/obstacles` — `sensor_msgs/PointCloud2` для систем поезда: по точке на объект
  в системе координат облака. Поля: `x y z`, `distance` (вдоль пути, м),
  `offset` (от оси, + влево, м), `height`, `track_id`, `confirmed` (1 — препятствие,
  0 — подозрение), `first_seen` (с какого расстояния замечен, м). Пустое облако —
  путь свободен или тракт ещё не готов (см. `/fod/status`);
- `/fod/markers` — `visualization_msgs/MarkerArray` для RViz: ось, габарит,
  препятствия (красные), подозрения (оранжевые), табличка с уровнем и скоростями.

Параметры узла — `config/train.yaml`: `topic`, `device` (`cuda` / `cpu`), `markers`,
`best_effort`, `forward`, `up`, `rpy`.

## Как работает

Мы не распознаём каждый возможный предмет. Мы строим, где проходит путь и габарит поезда,
запоминаем, как выглядит нормальное полотно, и тревожим на всё, что поднимается над нормой
внутри габарита и держится несколько кадров.

1. **Движение поезда.** Скорость — по развёртке стен тоннеля, положение в мире — small_gicp.
   Облако выравнивается с учётом движения за оборот лидара.
2. **Рельсы вблизи (до ~80 м).** Нейросеть по развёртке лидара (range image) находит головки
   путевых рельсов и контактный рельс; по ним — ось пути и уровень головок. Если сеть не
   находит пар (другая установка лидара), включается поиск по шаблону пары головок.
3. **Путь вдали (до 150 м).** Ось продолжается по профилю тоннеля и второй нейросетью по
   выпрямленному виду сверху из 10 накопленных кадров. Ось хранится в карте в мировых
   координатах, поэтому габарит не дрожит от кадра к кадру.
4. **Габарит и норма.** Вокруг оси — габарит ±1,05 м × 3 м над головками. Для каждой полосы
   поперёк пути запоминается обычная высота полотна (шпалы, лотки, крепления). На стоянке
   готовая норма не обновляется: иначе предмет, появившийся вблизи, через несколько секунд
   стал бы «полотном».
5. **Детектор.** Точки в габарите выше нормы собираются в группы и ведутся в мировых
   координатах; препятствие подтверждается, если видно в 4 кадрах из 5.

Модули: `fod/pipeline.py` — весь тракт; `fod/odometry.py`, `fod/lidar_odometry.py` —
движение; `fod/rail_seg_*.py` — сеть рельсов; `fod/contact_rail.py`, `fod/tunnel_axis.py`,
`fod/far_bev*.py`, `fod/track_map.py` — ось пути; `fod/obstacles.py` — детектор.
Веса сетей — `models/`.

## Результаты (наши стенды)

Объекты вставлялись в настоящие записи на ось пути, поезд подъезжает к ним;
ложные тревоги — на тех же записях без объектов и на 20 минутах `new_data`.

| Что | Результат |
|---|---|
| Ложные тревоги на чистых записях | 0,8 в минуту (14 за 17 минут), все ближе 30 м |
| Дальность, до которой известен путь | медиана 154 м |
| Человек на пути | подтверждён с 114 м (медиана) |
| Ящик 0,5 м | с 63 м |
| Куб 0,3 м | с 25 м |
| Щит 2 × 1,9 м поперёк пути (как в `cloud_with_fake_obj`) | с 130 м |
| Настоящий человек в `doubleT_obstacle` (поезд стоит) | подтверждён на 56 м, держится всё время, пока он в габарите |

Стенд: `python3 scripts/obstacle_bench.py --contact-rail --axis far --rails seg`
(нужны записи хакатона; путь к ним — `FOD_DATA=/путь/к/archive`).

## Быстродействие

RTX 5080 Laptop + Core Ultra 9 285H: 75–85 мс на кадр в контейнере (10 Гц), на записи
`doubleT_obstacle` (другой лидар, 920 тыс. точек в кадре) — ~170–220 мс, в живом режиме
там обрабатывается примерно 2 кадра из 3.

Если тракт не успевает за лидаром, узел всегда берёт самый свежий кадр, а старые
пропускает: отставание не копится. При 5 Гц (каждый второй кадр) ложных тревог столько же,
человек подтверждается на 109 м вместо 114. Офлайн-прогон считает все кадры.

## Ограничения

- Габарит ±1,05 м от оси: объекты сбоку дальше этого (у стены, на краю платформы) не видим.
- Сети обучены на наших тоннелях; там, где они не уверены, путь известен ближе, и детектор
  честно смотрит ближе, а не выдумывает габарит.
- Мелкие предметы (0,3 м и меньше) подтверждаются с 15–25 м.
